# 微软拼音候选窗定位：从已恢复基线逐项移除

## 已核实的环境与现象

- 用户宿主：AE 23.5 / CEP 11，Windows 微软拼音。
- 已安装 libcef.dll 文件版本：88.39.4+g634688c+chromium-88.0.4324.150。
- 系统扩展目录通过 junction 指向当前工作区 extension，排除了安装目录错误。
- 普通 input 和 CodeMirror 均曾错位；早先实测为「删除后候选窗定位恢复，但再次输入又错位」，未达到首次及连续输入均跟随光标的验收要求。
- 运行中已检查 browser / renderer 参数。第一轮 TSFImeSupport 禁用项，以及第二轮合并的 CalculateNativeWinOcclusion,TSFImeSupport 均实际传入，不能再归因于清单未加载或参数被覆盖。

## 实验与对照结果

1. 通过清单关闭 TSFImeSupport，让旧版 Chromium 走 IMM32。该路径选择有[对应版本的源码依据](https://github.com/chromium/chromium/blob/88.0.4324.150/ui/base/ime/init/input_method_factory.cc#L57-L62)，但用户实测仅在删除字符后暂时恢复位置，不能作为完整修复。
2. 在 Windows CEP / Chromium 88 中进行一次性延后 blur / focus，保留文字和选区；有输入、快捷键或合成时取消，避免打断输入。文本与选区回归通过，但用户再次输入仍错位，未通过真实候选窗验收。

3. 撤销 TSF 禁用项并让运行时重新加载配置后，用户确认「删除也不能正确定位，回到初版状态」。这支持关闭 TSF 与局部改善有关，但不等于已经找到完整修复。

4. 用户复测「仅恢复 TSF 禁用项、撤销其余输入法实验」后反馈，删除后的定位改善没有恢复。因此前一步不足以确认 TSF 是唯一影响因素。

5. 用户复测「关闭 TSF + contenteditable」后反馈，删除定位仍未恢复。本轮依照「换一项」撤下 contenteditable，切换为自定义合成按键保护。

6. 用户复测「关闭 TSF + 合成按键保护」后反馈仍未恢复。本轮撤下按键保护，改测合成提交后的光标滚动修正。

7. 用户复测「关闭 TSF + 提交后滚动」后反馈仍未恢复，要求在该基础上叠加 contenteditable；本轮保留滚动逻辑，仅增加输入模式配置。

8. 用户复测「关闭 TSF + 提交后滚动 + contenteditable」后反馈仍未恢复，要求改测「关闭 TSF + 焦点重绑定」。本轮恢复原版编辑器输入方式，移除 contenteditable 和提交后滚动，重新加入一次性 DOM 焦点重绑定。

9. 用户复测「关闭 TSF + 焦点重绑定」仍未恢复，要求尝试其他组合。本轮恢复早期首次出现局部改善时的完整编辑器配置：contenteditable、显式 spellcheck:false、合成按键保护、提交后滚动；关闭焦点重绑定。尚不能保证重现旧实测。

10. 上一组合仍未恢复，用户要求回到测试之前。本轮恢复完整组合，并从本次对话历史中提取最初新增 ime-focus.js 的补丁及其后续修订，恢复原始实现。前一轮重建版与原版不等价：原版支持 contenteditable、点击后重新排队，检查 document.hasFocus，并对非空标签草稿直接跳过重绑定。原文件恢复后 SHA-256 为 `e95d295173bc0ff870956d627e52e9f653dda8ba4cd8e7bff75899045ac8fa32`。

11. 用户确认恢复历史原始实现后，「删除后定位恢复」的旧状态已重现，并要求从该基线逐项移除。本轮只移除提交后自动滚动；其余代码与本地快照 `.artifacts/editor-ime/pre-isolation-restored/` 一致，待用户复测。本次反馈不能当作首次及连续输入均已正常的完整验收。

12. 用户确认移除提交后滚动后，删除不能恢复定位，候选词一直停在屏幕右下角。本轮先恢复滚动逻辑，再相对已恢复快照仅移除合成按键保护；不叠加上一轮移除项，等待用户复测。

13. 用户确认仅移除合成按键保护后，删除仍能恢复定位。因此它不是该局部改善的必要条件，保持移除。将此已验证状态保存至 `.artifacts/editor-ime/accepted-without-key-guard/`；在该基线上仅移除 contenteditable，恢复默认 textarea。用户最初反馈未恢复，拖动面板并多次尝试后确认「删除字符后能正确定位，但直接输入仍错位」。窗口状态会影响复现，不能把首次失败当作该输入模式必不可少的证据。

当前保留 `--disable-features=CalculateNativeWinOcclusion,TSFImeSupport`，CodeMirror 使用默认 textarea，执行自定义合成提交后滚动；原始焦点模块在 app 初始化时启用。本轮不启用自定义合成按键保护或 contenteditable；显式 spellcheck:false 保持不变。`CalculateNativeWinOcclusion` 是已核实的 CEP 原有禁用项。

焦点重绑定还原为历史版本，移除重建版专有的 isRebinding 标签保护；原版通过跳过非空标签输入避免误提交。其他 0.5.1 功能保留，第三方 CodeMirror 源码不修改。用户已在当前默认 textarea 组合的现场诊断中确认：普通输入框与编辑器均为直接输入错位、删除后恢复。

JS 更改重载扩展即可；启动参数需要宿主重新读取清单并创建 CEP 进程。本机已观察到 CEP 进程更换后仍由同一 AE 进程传入旧参数，因此对照前应核查实际命令行；若仍缓存旧配置，再保存工程并重启 AE。

没有修改系统输入法设置、AE 工程数据或 Adobe 二进制文件；没有发布，也没有生成安装器。

## 上游补丁的真正落点

用户提供的 [CEF Issue #3306](https://github.com/chromiumembedded/cef/issues/3306) 与症状高度一致，但尚未获取本机原生调用栈来证明全部根因相同。

[上游 c9b8f037 补丁](https://github.com/loongson/cef/commit/c9b8f03731c67ad3b3ef232c476cafe66da462b9) 修改的是：

- libcef/browser/native/browser_platform_delegate_native_win.cc：原生 HWND 获得键盘焦点，必须先于 WebContents 逻辑焦点及输入法客户端通知。
- patch/patches/views_widget.patch：嵌入窗口的鼠标激活路径也需要先设置原生焦点。只在 DOM 层反复 focus 不等价于该修复。

本仓库包含 HTML/CSS/JavaScript 和 ExtendScript，不包含 Adobe 的 CEP 嵌入层或可构建 CEF 源码。现有公开 CSInterface 也没有提供可等价替代该补丁的 Windows 原生焦点接口。已安装内核的 g634688c 提交无法在公开 CEF 仓库按该短 SHA 获取，不应假定官方通用构建可以直接替换 Adobe 定制内核。

要落实此上游修复，需要能重建并兼容 Adobe CEP 集成的原生运行时，或经专门设计/验证的原生适配层；这不是在当前扩展中添加几行 JS 就能可靠完成的工作。不能拿通用版 CEF DLL 直接替换，也不能保证仅升级 AE 就一定修复。后续若取得可构建的宿主源码/官方修正版，应先完成原生修复与独立兼容验证，再决定应用。

## 回归与验收边界

- `node tests/editor-ime-browser.cjs`：使用与宿主条件匹配的 UA、platform 和模拟桥接，确认原始重绑定的文字/选区保留、输入时取消、不误提交标签草稿；覆盖原生 input、textarea 与 CodeMirror textarea 的合成输入、英文、选区、粘贴事件路径、撤销重做、缩进、滚动、缩放与只读保护。本轮已禁用自定义合成按键保护，移除其专用断言；选词按键需要真实输入法复测。UA 不能模拟 CEF 原生输入法后端；上述检查均不作为真实候选窗定位验收。
- `node tests/editor-browser.cjs` 检查原有编辑器、格式化与快捷键；`node --test tests/*.test.cjs` 检查其余逻辑。当前组合的回归结果以本轮实际运行输出为准。
- 系统剪贴板、输入法选词快捷键和真实候选窗位置仍需在宿主实测，不能用合成事件代替。
- headless Chromium 使用 MockInputMethod，不能验证 Windows 系统候选窗。上述通过不改变「微软拼音定位未修复」的结论。
- Windows Computer Use 辅助进程多次启动失败，报 CreateProcessSecurityEnvironment failed (HRESULT = 0x80070020)；真实候选窗结论来自用户在 AE 内的实测反馈。

当前页面基线：关闭 TSF + 默认 textarea + 提交后滚动 + 原始焦点重绑定。用户已确认两处删除后能恢复定位，首次及连续输入仍未达到验收要求。

## 2026-10-21 原生焦点顺序原型

保持上述页面基线不变，通过临时调试端口记录 DOM 事件与几何，并只读采样目标 CEP 线程的原生焦点和系统 caret；日志不记录输入文字。现场复现中，首次合成开始前约 900 毫秒已完成 DOM 重绑定，原生焦点也已位于 Chrome widget。因而本次失败不能归因于重绑定被首键取消。后续创建的系统 caret 停在面板客户区原点，而 DOM 光标已位于输入框内部。最终焦点正确不能证明内部焦点通知的先后顺序正确，也不能单凭系统 caret 判断候选窗口的全部定位路径。

开发原型保存在忽略目录 `.artifacts/ime-native-prototype/`，尚未接入产品加载流程。它通过指定 CEP UI 线程的鼠标与窗口消息 hook，在旧 CEF 处理焦点通知前先设置原生 widget 焦点，验证是否能替代上游补丁的焦点顺序；不修改 Adobe 二进制，也不拦截键盘输入。监督进程核验扩展 ID、主页面路径、CEP 浏览器进程及其 AE 父进程，目标退出、窗口销毁、停止事件或 5 分钟到期时卸载。

隐藏隔离窗口的同进程及跨进程测试共 14 项通过，包括焦点顺序、范围拒绝、重复切换、卸载还原和前台窗口保持；监督进程的路径与进程范围检查通过。这些测试只验证原生机制，不代表微软拼音候选窗已经修复。用户保存工程并明确授权后，原型临时加载到工具箱 CEP 进程。用户反馈仍为直接输入错位、删除后恢复；该原型已停止，未接入产品。

随后准备了独立的坐标同步原型 `.artifacts/ime-caret-prototype/`。页面只测量原生 input/textarea 或 CodeMirror 的光标几何，不改变值、选区或焦点；临时本地通道只传递数字。目标 CEP 线程内同步已有系统 caret 和 IMM32 候选窗位置；不创建额外 caret，不改变窗口过程返回值，不拦截键盘，也不取消合成。坐标过期、越界、页面或 widget 失焦时停止应用；监督程序沿用精确进程核验和 5 分钟卸载。

该原型的 12 项原生隔离检查通过，覆盖跨进程坐标生效、其他输入框不受影响、错误目标拒绝和卸载停止；额外通过 DPI 换算、坐标新鲜度、越界和无效数字检查。浏览器几何检查覆盖内容/焦点/选区不变、水平滚动、textarea 换行及滚动、只读与敏感字段排除、CodeMirror 坐标。

真实宿主测试失败：只读采样已观察到系统 caret 从原点移动到页面光标附近，但用户报告 AE 卡死，无法完成候选窗验收。收到反馈后立即发送停止事件；监督进程记录卸载并退出，坐标通道也停止。坐标生效不能视为候选定位成功，更不能视为宿主兼容。原生输入法调用位于窗口消息处理路径，可能涉及重入或同步等待；目前没有线程栈证据，不把具体死锁原因写成定论。该原型不接入产品，也不自动启动。用户确认清理后 AE 恢复响应，但面板自动退出，随后已重新打开；没有要求用户重启 AE。临时调试描述文件已移除，诊断采集已停止。

用户补充观察：多个 CEP 扩展均出现类似现象，而其测试的 AEGP Panel + WebView2 面板没有。这加强了宿主输入法链路的怀疑，但不是所有 CEP 或 WebView2 的普遍结论；WebView2 迁移另行评估，当前原型不改变产品面板架构。
